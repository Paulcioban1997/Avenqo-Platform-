État : ouvert. Aucun mot de passe PostgreSQL ou clé de chiffrement n’a été changé. Aucune base ni aucun volume n’a été supprimé, recréé ou réinitialisé. Aucun historique n’a été réécrit et aucun force-push n’a été exécuté.

Le projet Railway alert-tenderness contient production et sandbox. Les connexions sandbox utilisent un autre mot de passe et ne correspondent pas à celui exposé. Les deux tâches de réconciliation sandbox n’ont aucune variable PostgreSQL directe : elles dépendent du backend. Les autres projets Railway accessibles inventoriés n’hébergent pas le backend Avenqo. Les environnements GitHub historiques ne prouvent pas l’existence de ressources encore actives. GitHub n’affiche aucune alerte native secret-scanning ; cela ne clôt pas l’alerte externe GitGuardian. La lecture des variables Vercel via le connecteur est indisponible ; les fichiers locaux web et backend examinés ne correspondent pas au mot de passe compromis.

PostgreSQL production et sandbox : version18.6 ; utilisateur applicatif actuel postgres, superutilisateur ; 77 tables publiques détenues par postgres ; aucune table publique avec RLS active. La production contient trois charges de connecteurs chiffrées, toutes lisibles avec la configuration actuelle (deux commerce, un calendrier). Sandbox : huit charges commerce lisibles et un calendrier non lisible. Ce dernier champ fait20 caractères et ne possède pas d’enveloppe Fernet : il doit être réparé par restauration sûre ou réautorisation OAuth avant un rechiffrement complet sandbox. Conserver la valeur actuelle ; ne jamais la remplacer par une valeur vide ni ignorer cette erreur.

CONNECTOR_ENCRYPTION_KEYS est actuellement partagé entre production et sandbox. Prévoir des clés nouvelles distinctes. Aucune preuve de publication de cette clé n’est affirmée ; la préparation de sa rotation répond au mandat et réduit le partage entre environnements.

Audit : tous les objets atteignables après récupération des branches et tags distants ont été inspectés par recherche de connexions PostgreSQL (11 315 objets,54 occurrences URL dans des versions de blobs ; ces occurrences incluent les fixtures). Gitleaks8.30.1 officiel, archive vérifiée par checksum, complète la détection des autres formats. Les anciennes alertes de tests sont vérifiées séparément ; aucune valeur n’est reproduite. Cette inspection ne prouve ni l’absence d’accès malveillant ni l’exhaustivité de tous les formats de secrets. Les copies externes et forks restent à traiter après révocation.

## Rotation PostgreSQL progressive — autorisation de production requise

1. Vérifier une sauvegarde récente complète, son intégrité et une restauration dans un environnement isolé. Recueillir les références de volumes, version Alembic et inventaire des tables. Le succès du cron seul ne prouve pas la restauration. Conserver les sauvegardes et la base existante.
2. Répéter la transition sur les fixtures PostgreSQL isolées, puis sur le sandbox si autorisé. Émettre les nouvelles valeurs uniquement dans le gestionnaire sécurisé ; jamais dans Git, une conversation, les arguments d’une commande ou un journal.
3. Créer un rôle propriétaire NOLOGIN pour les objets applicatifs et des utilisateurs distincts : API, migrations et sauvegardes. L’API reçoit CONNECT, USAGE, DML sur tables et droits nécessaires sur séquences. La sauvegarde reçoit la lecture des objets nécessaires à pg_dump. Le migrateur reçoit l’appartenance au rôle propriétaire et les droits CREATE du schéma. Transférer sélectivement les objets applicatifs après inventaire, dans une transaction ; ne pas employer REASSIGN OWNED global sur postgres et ne pas accorder le rôle postgres à l’API. Préserver les extensions et leurs propriétaires administratifs. Configurer les privilèges par défaut pour les objets futurs.
4. Le démarrage Railway exécute alembic avant uvicorn. Alembic prend déjà en charge ALEMBIC_DATABASE_URL : lui fournir la connexion du migrateur, distincte de DATABASE_URL pour l’API. Vérifier que le rôle des créations et privilèges futurs est bien le rôle propriétaire ; ceci doit être testé avant bascule.
5. Tester les nouvelles connexions : lecture/écriture applicative, migrations existantes, /api/v1/ready, accès client, consommation de crédits, connecteurs, génération PDF, pg_dump et restauration isolée. Vérifier l’absence d’augmentation des erreurs d’authentification et conserver l’ancien accès pendant cette validation courte.
6. Remplacer DATABASE_URL de l’API puis celle du cron de sauvegarde, avec les nouvelles valeurs sécurisées. Déployer progressivement et vérifier chaque service. Les anciens et nouveaux utilisateurs coexistent pendant la transition ; cela permet une continuité d’authentification. Le projet a actuellement une seule réplique : une absence totale d’interruption HTTP ne sera pas garantie sans vérification du déploiement avec chevauchement et santé.
7. Après preuve que tous les consommateurs utilisent les nouveaux accès, révoquer le mot de passe administrateur exposé avec la régénération supportée par Railway, qui synchronise le serveur PostgreSQL et ses variables. Une simple édition POSTGRES_PASSWORD ne change pas le mot de passe d’une base déjà initialisée. Conserver un accès administratif renouvelé et sécurisé. Ne pas désactiver aveuglément le rôle postgres requis par l’administration Railway.
8. Vérifier qu’une nouvelle connexion avec l’ancien mot de passe est refusée, sans afficher la valeur ni les erreurs contenant la connexion. Examiner les sessions restantes et fermer uniquement celles explicitement identifiées comme anciennes, si autorisé. Vérifier une sauvegarde utilisant la nouvelle connexion. L’incident PostgreSQL reste ouvert avant cette preuve de révocation effective.
9. Après révocation, tout retour arrière utilise les nouveaux accès ; ne jamais réactiver le mot de passe exposé. Prévoir une fenêtre courte et annoncée si la bascule progressive ou le dernier changement administratif rencontre un blocage.

Références : https://docs.railway.com/databases/database-view ; https://www.postgresql.org/docs/18/role-membership.html ; https://www.postgresql.org/docs/18/sql-alterdefaultprivileges.html .

## Rotation CONNECTOR_ENCRYPTION_KEYS — procédure indépendante

1. Générer une nouvelle clé par environnement dans le canal sécurisé, sans affichage. Préserver temporairement la clé actuelle.
2. Déployer d’abord les lecteurs compatibles avec les deux clés dans l’ordre ancienne,nouvelle ; ainsi toutes les anciennes répliques lisent encore les nouvelles écritures pendant cette première phase. Puis déployer partout l’ordre nouvelle,ancienne une fois tous les lecteurs compatibles. Ne pas faire écrire avec la nouvelle clé pendant que des répliques anciennes ne savent lire que l’ancienne.
3. Exécuter scripts/rotate_connector_secrets.py en mode dry-run, qui vérifie la lisibilité des deux magasins sans écrire. Le sandbox ne peut pas passer cette vérification tant que le calendrier non-Fernet n’est pas réparé. La production a trois charges actuellement lisibles.
4. Après autorisation, exécuter --apply avec --confirm-environment correspondant explicitement. Le service verrouille les lignes, rechiffre avec la clé primaire, vérifie les données et la lecture par la clé primaire ; une erreur annule toute la transaction. Il préserve les données et l’horodatage Fernet. Les logs ne donnent que des compteurs.
5. Revérifier toutes les charges avec la nouvelle clé seule, tester les connecteurs commerce/calendrier et empêcher les anciennes répliques d’écrire. Retirer l’ancienne clé de la configuration active seulement après zéro charge dépendante et validation fonctionnelle. Ne jamais considérer le retrait d’une clé comme une révocation des tokens OAuth auprès des fournisseurs.
6. Les anciennes sauvegardes contiennent encore des charges chiffrées avec l’ancienne clé : conserver la clé de récupération dans un coffre distinct jusqu’à expiration ou migration vérifiée de ces sauvegardes. Retirer la clé de l’application ne doit pas rendre les restaurations impossibles.

## Code corrigé et contrôles

Les quatre scripts actuels n’ont plus de secret PostgreSQL codé en dur ni de secours implicite. Le script de vérification de dataset utilise une session API explicitement autorisée et ne fabrique plus de session utilisateur en base. Les fixtures de connexion deviennent explicitement fictives. Les exemples de clés sont omis du template .env. Le contrôle local avant commit et Gitleaks détectent les connexions codées en dur et les formats de secrets courants sans afficher leurs valeurs ; le job GitHub security-incident-guard réexécute les contrôles.

La rotation des connecteurs couvre commerce_connections.encrypted_credentials et crm_calendar_connections.encrypted_credentials. Elle accepte une liste JSON ou CSV de clés et préserve leur ordre. Les tests couvrent double lecture, écriture avec la clé primaire, rejeu, timestamp, dry-run et annulation globale lors d’une erreur. Le test PostgreSQL CI crée uniquement des rôles et un schéma jetables dans une base locale dédiée : double accès, lecture/écriture, DDL avec migrateur puis refus de l’ancien login. Aucune commande de ce test ne cible Railway et aucune base n’est supprimée.

Établir le mapping des commits et les impacts sur branches, tags, PR et déploiements. Présenter la différence et obtenir une autorisation spécifique avant toute publication de l’historique réécrit. Les forks et copies restent hors du contrôle du dépôt. Le nettoyage ne remplace jamais la révocation.
